## Where things stand

Phases 0–5 are done. The branch was broken when this started — no icons, no DataTables, no widgets, a dead documents module — and is now working and covered.

| | |
|---|---|
| Python suite | 294 passed, 27 skipped; every tier runs standalone |
| Browser suite | 23 tests (`make test-e2e`), stable across runs |
| `bootstrap-compat.css` | deleted (968 → 248 lines of real components) |
| LESS | all 115 files gone; wheel 8.2 MB with none in it |
| Built assets | ship in the wheel: `pip install` needs no Node |

**The pattern worth carrying forward:** every serious bug this cycle was invisible to the Python suite, because a page missing its scripts, its styles or its handlers still returns a perfectly good 200. CSP blocking every inline script, `bootbox` throwing on a missing Bootstrap plugin, the navbar search gated on an attribute that does not exist, `folder_edit.js` bound to a class no template carries — all found in a browser, none findable without one. So the remaining work is mostly testing, and the next gap is the one no assertion covers: **whether it looks right**.

## Phase 6 — Visual parity

The goal is not "no exceptions". It is: put the old UI and the new one side by side, page by page, and account for every difference as either an improvement, an acceptable change, or a regression to fix.

### 6.1 Build the comparison rig

A second app instance serving the **pre-migration** UI, so comparisons are against something real rather than memory.

- `git worktree add ../sbe-baseline main` — that tree still has the LESS pipeline and Bootstrap.
- Run it on port 8898 with the same seed data (`seed.py` works unchanged), `npm install && flask assets build` for its assets.
- Current branch stays on 8899.
- One capture script drives both, so pages, viewports, login state and seed data are identical. Only the front end differs.

### 6.2 Decide what to capture

Per page: **desktop 1440×900, tablet 768, mobile 375**, full-page. Plus the states a page-level shot misses.

| Surface | Pages | States |
|---|---|---|
| Auth | login, forgotten password | empty, validation error |
| Community | wall, members, settings | — |
| Documents | folder listing, gallery view, document detail, permissions | modal open (new folder, upload, move, delete confirm), row selected, empty folder |
| Wiki | page, edit, history | rich-text editor loaded |
| Forum | index, thread, new thread | attachment field |
| Admin | dashboard, users, groups, audit, settings | chart rendered, DataTable paginated |
| Global | navbar user menu open, search box, flash messages, 404, 403 | — |

That is roughly 20 pages × 3 viewports plus ~12 states. Captured to `scratchpad/shots/{baseline,current}/`.

### 6.3 Review

I read every pair and record a verdict — **parity / improvement / regression** — with a one-line note. Layout, alignment, spacing rhythm, type hierarchy, contrast, density, and whether anything is missing, overlapping or unstyled. Output is a findings table, not a wall of images.

### 6.4 Already found

Three pages screenshotted so far, and the review is already earning its keep. These are open defects:

1. **The navbar user menu renders twice**, and the avatar overlaps the first label — reads as "(A)dmin ⌄ Admin ⌄". Every logged-in page.
2. **The folder listing's table header sits *below* its rows.** "Title / Size / Owner / Age" renders under the last row. Almost certainly the `-mt-14` on `#objects-table` fighting DataTables' wrapper.
3. **DataTables pagination is unstyled** — "Showing 1 to 2 of 2 entries / ← Previous / 1 / Next →" stacked as bare text. `datatables-setup.js` renders Bootstrap-3 pagination markup that no longer has styles.
4. **The footer separator is a solid black rule.** Everything else on the page uses `gray-200`.
5. **The login heading reads "Login to"** with nothing after it — `SITE_NAME` is empty and the template does not handle that.
6. **Document thumbnails render as a large empty box** with a stray glyph.
7. Sidebar menu entries ("Activity stream", "All files in this community") are plain text with no link affordance.

### 6.5 Lock it in

Once regressions are fixed and the current state is blessed, add Playwright's `expect(page).to_have_screenshot()` for a small set of key pages, with the approved images committed. That turns "it looked right in September" into something CI enforces. Pixel diffs are noisy for whole pages, so scope them to stable regions (navbar, a listing row, a modal) rather than full-page.

**Acceptance:** every difference from the baseline is accounted for; no regression left open; screenshot tests green twice in a row.

## Phase 7 — Design pass

Parity is the floor. This phase is the "better looking" part, and it is where taste is involved — so it produces proposals to look at, not a fait accompli.

### 7.1 Take stock of the design system

The Tailwind components were ported module by module from LESS, which is a translation, not a design. Before changing anything, measure what is actually in use: how many greys, how many blues, how many spacing values, how many radii, how many shadows, which font stacks. Inconsistency here is why a UI reads as "unfinished" even when every page is individually fine.

### 7.2 Direction

Load the `frontend-design` skill and settle a direction (typography, density, colour, elevation) before touching surfaces, so the result is coherent rather than twenty local improvements. Present two or three options as rendered screenshots of the same page, not as description.

### 7.3 Apply, surface by surface

Navbar and community tabs → listings and tables → forms and modals → empty states → buttons and badges. Each one re-screenshotted and reviewed before moving on.

Empty states deserve their own mention: the wall with no activity is currently a titled box containing nothing, which is the cheapest thing to improve and among the most visible.

### 7.4 Accessibility, which is measurable

Not a matter of taste, and checkable in the browser: contrast ratios against WCAG AA, a visible focus ring on every interactive element, keyboard reachability (the modals especially — native `<dialog>` gives focus trapping for free, the Alpine ones do not), heading order, landmarks, and `alt` text. Worth an automated axe-core pass in the browser suite.

### 7.5 Responsive

375 / 768 / 1440 for every surface. The old UI was Bootstrap-3 responsive; the new one must not be worse. The navbar mobile menu and the document listing are the two most likely to break.

**Acceptance:** design tokens are consistent and documented; AA contrast throughout; no horizontal scroll at 375; before/after screenshots reviewed and approved.

## Phase 8 — Finish the test pyramid

Tepyd's remaining findings, and the gaps the browser suite has shown up.

- **Unit tier is 11% against a 60% target.** The tier layout makes this cheap now (`pytest tests/a_unit` runs in 14s). Push assertions down: anything not needing a database or HTTP.
- **`cli` and `testing` have no tests at all.** `setup` got its first this cycle.
- **Forms end to end**, which the browser suite still does not cover: create a forum thread *with an attachment*, edit a wiki page *through the rich-text editor*. Both exercise upload and CKEditor for real rather than checking they initialised.
- **`test_all_simple_endpoints_as_admin` collects errors and only prints them** — it passes unconditionally and always has. Fix or delete.
